## 主要结论

1. **拖图存在缓存未命中时的长帧。** 桌面真实指针拖动无C#请求，但出现86–90ms绘制尖峰；首次经过新区域的固定轨迹出现147–393ms单帧。地形整块重建、海岸/边界模板的JS逐像素生成是明确入口。热缓存时常态约2–3ms，平均值掩盖了卡顿。
2. **AI存在大量重复世界验证和候选模拟。** 287个AI步骤调用完整世界验证10528次，其中7103次再次检查同一快照对象；321单位样例为10067次、7260次重复。完整验证调用链约占所测快进后端时间45%左右，但不能把其中每一项都算作可删除开销。
3. **正常演出/未启用真正批处理时，全量状态回传十分昂贵。** 两个样例一轮累计返回666MB/874MB JSON；批处理仅约8MB/12MB。是本机宿主到前端的数据，不是互联网下载。普通模式的传输、解析、分配会加重动画卡顿。
4. **完整世界复制、战略全图反向寻路、强制落盘也是独立热点。** 不能只做兵牌LOD，也不能只“多开线程”。先减少工作量，再安排显示与计算重叠。

## 实机证据与目标

[两张原图及哈希](references/performance_user_20261023/README.md)已保存。R版设备截图为iQOO Z11/天玑8500/12GB物理内存展示，原版设备据反馈为麒麟990。

| 用户反馈 | 原版 | R版 |
| --- | ---: | ---: |
| 骑兵走两格 | 0.34秒 | 1秒 |
| 第一征服开局直接过回合 | 5.92秒 | 52秒 |

反馈者确认勾选了加速选项，未勾选时约2分半。跨设备观察差距约2.94倍、8.78倍，不作为严格同机实现比。该信息排除了把最新反馈简单解释为“没开加速”；源码仍应记录运行时是否实际进入批处理，核对设置与按钮共同条件。

移动总时长需要拆分输入→请求返回→资源准备→动画首帧→动画结束。目前`movementStepMs()`普通移动为`255/√speed`毫秒，默认speed=2；若路径恰好两条边，预设演出约361ms，并非写死1秒。用户的1秒不能直接全归因预设动画，也不能仅把时长改短而不解决长帧。截图未包含CPU占用曲线；“全核满载”“源码外置所以读取慢”均无测量证据。

## 重算的具体来源

### 1. 完整世界和兵种规则反复验证

`WorldActions.Ready()`首先`state.Validate()`；PlanStep→PlanProduction/PlanNextUnit→PlanUnit→各类候选及ExecuteStep等多层调用Ready/Validate。`WorldState.Validate()`遍历地块、单位、事件，重建多个身份集合、字典、GroupBy，还深入验证每个兵种的配置和技能槽。

| 计数 | conquest1 | conquest4 |
| --- | ---: | ---: |
| 完整世界Validate | 10528 | 10067 |
| 涉及不同WorldState对象 | 3425 | 2807 |
| 同一对象再次Validate | 7103（67.5%） | 7260（72.1%） |
| 地块验证访问总量 | 56556416 | 54079924 |
| 单位验证访问总量 | 2672631 | 3383679 |
| UnitProfile.Validate | 3191620 | 4040332 |

deep热样本的世界Validate包含子验证约5.19/6.08秒，占Dispatch约46.9%/44.7%。这是被测调用链占比，**不是保证可删除45%耗时**；同对象次数占比也不能直接当耗时比例。

优化边界：外部命令、读档、Mod输入和实际提交后的新状态仍完整校验；内部已验证快照使用显式上下文/受信入口，静态规则在冻结后验证一次。不能简单删Validate或按revision建立全局缓存：候选快照可能同revision但内容不同，IReadOnly集合也并不保证底层不可变，脚本扩展边界必须保留。

### 2. 战术评分把“试走”变成完整世界操作

`WorldAi.TacticalMoveCandidates()`先获得可达集合，又为每个候选格调用`WorldActions.Move()`。后者重新调用MovementRange，处理领土/事件/胜负，并深复制整个世界；候选结果再调用StrikeCandidates验证和扫描目标。完整合法性不能省，但多数候选不需要独立复制全部未变对象。

诊断样例：conquest1仅70次TacticalMoveCandidates，却有1095次WorldActions.Move；conquest4是39次和634次。Move统计还包含真实执行和其他调用，不能将其全部算成战术模拟。全局WorldState.Copy分别1651/1409次，累计分配约1703/1577MiB，包含耗时约0.86/0.84秒。

建议建立共用移动规划结果及只读候选投影，复用同快照的路径/占格/规则；仅变化对象复制，选定后再执行完整提交。遇占领事件、外交/胜负和Mod脚本等影响决策的情况，仍需完整等价模拟，不能只把unit.cell换掉就评分。

### 3. 战略目标逐个做全图反向搜索

`WorldAiStrategy.StrategicCandidates()`按敌方势力遍历目标，对每个目标再次遍历全图构造落点，再调用`Movement.DistancesTo()`。两局反向搜索5119/6057次，deep约1.05/1.13秒。相比之下，普通`HexMap.Reachable()`在原诊断样例只累计几毫秒，不能笼统把一切称为“寻路慢”。

优先用按移动规则建立的连通性过滤不可能目标，按目标格/射程直接构造局部落点，复用相同通行条件下的距离场。领土、敌我占格、运输、河流桥梁、能力和规则版本都影响合法缓存范围；保留目标排序、同分选择及随机消耗。

`PlanNextUnit()`每一步又从按格排序后的单位队首开始，PlanUnit分别2937/3574次，明显超过AI步骤数。可用行动候选队列/索引减少已完成单位的重复验证，但召唤、生产、事件恢复行动和调度顺序必须保持。

### 4. 存档不是每步写，但每势力交接仍很重

`InstallSession()`在势力/轮次/结果等边界AutoSave。两局各19/24次，不是287/368次。StoreAccount虽每步进入，却会按账户revision跳过未变化的写盘，不能说账户每步都落盘。

deep热样本Save包含耗时约1.90/3.07秒，占17.2%/22.5%；其中write+Flush(true)约1.09/1.95秒。保存链还包括WorldSave编码→JSON解析→SessionSave再编码→ClientSlot将byte[]包装为Base64→同步持久化。

建议先减少同一保存对象的重复编码/拷贝，评估保留校验和兼容格式的流式写入；后台单写入队列必须绑定不可变快照、有序提交、原子替换、暂停/退出等待，不能拿“直接关闭Flush或少存档”冒充等价优化。桌面磁盘耗时不能直接当手机闪存耗时。

### 5. 快进View不是最大热点，但普通全量响应必须改

快进deep中View只约39/33ms，响应序列化约109/155ms。前一轮“优先优化快进View”的判断应下调，当前最大头是上述核心重算。

普通每步返回全部cells和units，造成666/874MB累计JSON；应给普通动画也使用基于revision的地块/单位增量与动作事件，保留首帧/读档/失步完整重同步。所需移动路径应来自执行结果，避免View为展示路径再次求可达范围。不能只优化快进而让正常观看继续大量传全图。

## 前端重绘的量化结果

| 场景，120次rAF采样 | 常态/平均绘制提交 | 最大帧 | 地形缓存重建 |
| --- | ---: | ---: | ---: |
| 近景拖动，paired样例 | 平均5.18ms，p95 3.10ms | 146.8ms | 5 |
| 远景拖动，paired样例 | 平均8.21ms，p95 4.00ms | 384.3ms | 3 |
| 同轨迹远景热缓存，119可见单位 | 平均2.62ms | 3.70ms | 0 |
| 移动呈现冷缓存夹具 | 平均2.96ms | 97.9ms | 1 |
| 移动呈现热缓存夹具 | 平均2.17ms | 3.30ms | 0 |

真实指针拖动两次记录46/50帧，最大89.9/85.6ms，均一次地形重建、0次API请求。视窗拖动卡顿不能直接归于C#正在重新求AI；但过回合的后端响应处理、JS主线程绘制及手机CPU/GC竞争会共同影响体验。

追加surface探针确认新远景区域869次coast调用中199次未命中，coast方法累计223ms；近景75次新海岸模板累计127ms。`map-surface.js/rasterize()`在JS中按像素遍历三角形、插值颜色/纹理并创建临时数组，再putImageData；这比“普通Canvas drawImage画图”重得多。国界模板也是同类生成路径。此处适合进关有限预热、按需后台/分时生成，且按相邻地块颜色/归属正确失效。

改进应把一个大视口缓存改为可复用地图块，分开静态地形与归属等动态层，限制每帧新块/模板生成预算。图片加载不应让无关地形缓存一起失效。预热本身不能让内存无限增长，coast现上限512、兵模帧约8M像素，须记录淘汰与再次生成。

**兵牌LOD属于必做范围，其效果须与其他优化分别验收。** 已有兵模帧缓存，热远景跳过兵模位图绘制的诊断对照约2.62→2.46ms；追加采样3.15→2.29ms，存在波动，不据此宣称固定提速比。该对照仍计算姿态并画兵牌/头像，完整LOD会省更多工作；手机GPU收益未知。缓存生成尖峰和完整LOD均须处理，先后顺序不表示取舍；当前只记录方案。

**动画节流是独立问题。** 120次约60Hz的rAF中idle只画60帧，符合当前30Hz非脏帧节流；拖动置脏可画120帧。当前动效即便CPU有余量，也可能视觉上只有约30fps，不能全部称为算不动。应按交互/移动/攻击活动状态调度60Hz并测实际预算，静止场景按需绘制；不是全面解除节流。

状态准备也存在冗余：state对象引用变化会重建索引/排序并JSON.stringify全地块作为地形签名。人为每帧替换等内容对象时平均绘制约5.23ms、地形重建0次，说明“不重建地形”仍可能有全量准备。该实验是压力对照，真实移动并非每帧都有新state；应让增量更新携带独立的地形/单位版本，避免用整张地图序列化判断是否需要重画。

## 实施顺序与恢复入口

1. **C#先改重复验证与候选移动投影。** 目标是减少同快照全量扫描、复制和重复配置检查；保留外部入口及提交后校验。验证完整会话、双RNG、事件与错误路径等价。
2. **普通和快进统一增量状态协议。** 让动画模式也免于每步约2.3MB全量响应；监测JSON字节、解析耗时及主线程长任务。
3. **地图分块与海岸/边界模板预热。** 从已捕获的86–393ms尖峰入手；同时加入兵牌LOD和活动动画帧率调度，验证真实拖动、缩放与移动。
4. **战略距离场/行动队列及存档管线。** 分别测收益，不靠缩短搜索或删存档边界改变游戏行为。最后才考虑计算/动画有界流水线和更换绘制后端。

以实机52秒反馈作为回归基线，未来实施后先争取同版本修复前后、同存档同设置至少减半，再向原版量级推进。没有实机新结果不能称“52秒已降到某值”；更不能按桌面45%占比推算出手机精确节省秒数。当前实施暂停，仅维护报告；收到用户明确启动实现的指示后，再按上述顺序推进全部项目。本报告及summary.json足够恢复，无需重读完整会话或重复跑全部基线。
