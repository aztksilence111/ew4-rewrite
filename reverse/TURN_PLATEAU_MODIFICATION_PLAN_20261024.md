# 连续回合平台耗时：后续代码修改规划

日期：2026-10-24。

本文件按用户要求规划开发侧如何修改，不展开手机测试方式。本轮只新增本文档，不修改游戏实现、配置、构建产物或既有状态日志。下述内容均为待实施方案，不代表已实现或收益已确认。

## 1. 本次判断与修改目标

最新反馈：最初首次过第一回合曾出现一次12秒，从第二回合起为15–16秒；后续多次测试首轮通常15–16秒，清内存重进、重新安装也未能复现12秒。连续推进后，每回合大约增加1–2秒，最终在25–26秒附近稳定。

以15–16秒作为当前稳定首轮参考，12秒仅保留为一次历史结果。重点削减后期局面带来的额外计算与分配，不把恢复偶发12秒当成优化路线。平台期比稳定首轮增加约10秒，说明仅改善启动、进图或首次编译不足以覆盖问题；手机上的具体耗时构成仍未被确定。

已有开发侧证据支持优先处理搜索与候选构造：

- 固定六轮中，单位数252→286、AI步骤285→313，而搜索访问格约342万→946万。后续已实施的分配优化没有减少这项搜索工作量。
- 当前候选移动虽避免了多数完整校验，仍逐格确认字段未改；第六轮额外所有权检查约759万格。
- 世界复制次数仍为首轮612次、第六轮824次；最近一批优化后，每轮累计分配仍约1151–1764 MiB。累计分配不是常驻内存。
- 六轮距离场查询17475次，既有命中15次、清空后重用17次。单纯扩大现有缓存不是主要突破口。

这些数字来自此前冻结桌面实现，只用于确定修改顺序，不当作当前手机耗时占比或收益预测。

## 2. 批次一：战略搜索只求调用方需要的距离

主要文件：`rewrite/Ew4.Core/HexMap.cs`、`rewrite/Ew4.Core/WorldAiStrategy.cs`。

### 当前重复工作

`Movement.DistancesTo` 从目标端点反向执行Dijkstra，直到队列耗尽。`StrategicCandidates`随后实际只读取单位起点，以及该单位本回合`reachable.Keys`中的格子，并只使用距离小于起点距离的落点。对其他格子求出的最终距离通常不会被本次决策读取。

同一个目标循环内还反复执行`reachable.Keys.OrderBy(...)`，可达格集合和升序顺序实际上没有变化。

### 计划修改

1. 保留完整距离场接口，为战略规划增加内部的受限查询入口，显式传入单位起点和可达落点集合。其他需要完整结果的调用方不受影响。
2. 先采用容易证明等价的停止条件：所需格子的最短距离全部确定后结束搜索；若有不可达需求格，则允许搜索至队列耗尽，不把暂未访问误判为不可达。
3. 在此基础上加入更有效的起点距离边界：单位起点以有效最短距离出队后，只需确保所有距离严格小于起点距离的候选落点均已确定。非负边权成立时，可用队列最小距离边界结束，不再扩展更远区域。零费用边、重复队列项和目标端点含起点都须纳入边界推导。
4. 受限结果只暴露已确定的查询距离，不能将尚未确定的暂定距离当成最终距离；缺失项须与接口约定一致。
5. 每个运输分支提前生成一次升序可达格数组，所有目标共用；不再逐目标排序。
6. 保持现有端点集合、边费用、海陆/运输规则、桥梁方向、超额进入规则、长整型距离和溢出检查。目标遍历与落点选择的顺序不变。

### 实现边界

不删目标，不减少候选，不把精确距离换成六边形直线距离，不提前跳过仍可能影响随机调用的目标。受限距离结果不得混入要求完整距离场的缓存；如使用局部缓存，应限定在同一世界、单位、运输分支和需求集合内。

优先收益来自减少搜索访问格，而不是进一步扩大缓存。若起点本来就离目标很远，搜索缩减可能有限，因此本项不承诺固定百分比。

## 3. 批次二：从领地写入源头记录变更，消除候选整图比对

主要文件：`rewrite/Ew4.Core/TerritoryClaims.cs`、`rewrite/Ew4.Core/TerritorialJurisdictions.cs`、`rewrite/Ew4.Core/WorldActions.cs`、`rewrite/Ew4.Core/PlanningScope.cs`。

### 当前重复工作

`MoveCore`拿到新的地块集合后，扫描全图生成`cell.owner_changed`，再次扫描找原领主。`PlanningScope.ProjectMovement`又扫描所有格子，确认除了归属之外的字段都没有变化。局部移动因此反复付出整图成本。

### 计划修改

1. 在领地及辖区处理的实际写入位置记录格子索引与原归属，结束时形成最终变更集合。两阶段修改合并去重，剔除最终恢复原值的格子。
2. 变更集合由内部受控构造器产生并绑定基础世界；不能由外部调用方提交一个任意列表以绕过检查。受控入口只提供归属修改能力，不能同时修改地形、建筑等其他字段。
3. 先保留现有返回地块集合的方式，只把“再次整图找差异”改为消费变更集合，避免第一步就重写全部世界存储结构。
4. `ProjectMovement`仅核验变更格归属、移动单位、出发/目标格容量与阵营等受影响约束；其余约束仅在基础世界已通过同步作用域验证、受控写入能力确实封闭时继承。
5. `MoveCore`从最终变更集合生成通知与原领主列表。变更格按原先全图扫描的索引升序处理，原领主保持原有首次出现顺序，保留通知和投降处理顺序。
6. 辖区连锁占领影响到的所有格子都必须进入集合，不能仅记录移动路径或目标格。暂不具备受控能力的分支继续原有完整处理。

### 实现边界

本批只替换可以证明多余的差异发现与校验扫描。投降、脚本、事件、胜负结算可能引起广泛变化，不能继承此前局部移动的证明；产生的新状态按既有完整路径处理。实际提交的完整校验先保留。

不要把“有变更列表”直接等同于安全增量校验；安全性必须来自受控写入入口与基础状态身份。不得信任可在外部继续修改的数组或字典。

## 4. 批次三：同一规划作用域内复用查询准备工作

主要文件：`rewrite/Ew4.Core/WorldAiStrategy.cs`、`rewrite/Ew4.Core/WorldActions.cs`、`rewrite/Ew4.Core/WorldAiUnits.cs`、`rewrite/Ew4.Core/PlanningScope.cs`；必要时新增内部规划查询上下文。

### 当前重复工作

战略规划会构建势力索引、驻军分组，并在每个敌方势力下扫描全图；驻军战力、位置事实等也可能被重复计算。移动上下文还会构建阵营与占格信息。反复生成这些集合会放大后期单位和目标数量增长的成本。

### 计划修改

1. 在单个同步规划作用域内，按世界对象身份建立只读查询上下文，提供单位ID索引、按格驻军、势力索引和归属格索引。
2. 一次构建按势力关联的目标格列表，覆盖格子归属与驻军归属两种来源；每个势力内部按格子索引升序去重。替代“每个敌国重新扫描全图”，保留现有筛选语义。
3. 将仅依赖当前世界与固定规则的驻军战力、目标位置事实按需计算并复用。与行动单位、外交视角、射程、运输或规则实例有关的量，必须留在相应上下文，不能误做全局常量。
4. 移动上下文复用已经准备的基础占格和外交查询结果；行动者专属移动能力仍单独构造。先消除同次规划内的重复建表，再考虑跨单位复用。
5. 候选世界与基础世界即使拥有相同Revision，也不能共用含动态状态的查询。键至少依赖实际世界身份与必要规则/视角，作用域退出即释放引用。

### 实现边界

不建立跨回合无上限缓存，不仅凭Revision复用，不扩大那份已有低命中率的距离场缓存。候选顺序、同分顺序、目标排序与随机数调用次序保持原样；可扩展规则只在能确认纯查询的范围内复用。

## 5. 批次四：减少候选快照复制，维持对外隔离

主要文件：`rewrite/Ew4.Core/WorldState.cs`、`rewrite/Ew4.Core/PlanningScope.cs`、`rewrite/Ew4.Core/WorldActions.cs`、`rewrite/Ew4.Core/WorldAiUnits.cs`。

本项依赖批次二的受控写入边界，优先级低于搜索和整图扫描。

### 计划修改

1. 区分内部只读候选投影与真正提交的世界。内部候选在受控作用域中只替换变化的单位/地块，未改部分仅在已冻结或保证不可写时共享。
2. 第一阶段允许仍复制顶层数组，只减少深层对象和集合的重复复制；不直接将公开`WorldState.Copy()`改成浅拷贝。
3. 若顶层数组复制仍构成主要成本，再考虑内部“基础集合加稀疏覆盖”的只读视图，要求索引、遍历顺序及所有读取方完全兼容；不得让其流入要求独立持有数据的存档或公开可变接口。
4. 真实提交、脚本扩展或未知写入需要独立拥有数据时，按边界物化。避免候选创建、提交和后续动作对同一未变数据连续重复深拷贝。
5. 死亡ID、事件历史等只考虑已证明不可变时的共享；保留所有游戏语义和保存内容，不为降低分配裁剪历史。

### 实现边界

`IReadOnlyList`或record本身不保证底层集合不可变。共享前必须封闭写入能力；对象池只用于不逃逸的临时工作区，不能归还仍被候选、缓存、旧快照或异步保存引用的数组。嵌套规划必须有独立租借生命周期。

## 6. 后续辅助项与明确暂缓项

| 方向 | 后续处理 |
| --- | --- |
| 搜索数组分配 | 在受限查询落地后，对不逃逸的工作数组按需复用；缓存结果必须独立拥有数据，不能与已归还数组别名共享 |
| 保存编码 | 既有缓冲复用已实现；下一步仅在确有重复物化处减少中间对象，保留编码、原子替换、备份及持久化语义 |
| Android AOT | 保留为独立运行时优化方向；当前不直接改默认发布模式，不把它当作减少搜索工作量的替代方案 |
| 前端快进 | 若后续需要修改，优先合并纯展示更新与最终画面刷新；不能跳过玩法步骤、事件、对白或持久化点。本批不据手机总耗时直接认定它是主因 |
| 强制GC、每轮清缓存 | 不采用，无法消除搜索与重复扫描，也可能增加停顿和重建 |
| 扩大距离缓存 | 暂缓，既有真实重复查询太少；优先减少单次计算范围 |
| 死亡历史裁剪 | 不采用，现有占比小且承载事件与存档语义 |
| 减少自动保存或Flush次数 | 不作为当前提速手段，避免以恢复能力换速度 |
| 削减AI目标、缩短思考、跳过校验 | 不采用，目标是相同决策与约束下少做重复工作 |
| 继续增加进图预载 | 不纳入本轮回合优化主线，不能解释和解决后期平台耗时 |

## 7. 实施顺序与完成标准

建议逐批实施，不把所有改动一次合入：

1. **战略受限距离查询和可达格排序复用。** 直接削减后期增长最明显的搜索访问量。
2. **领地变更集合与局部校验。** 去掉通知、原领主提取和候选校验中的重复整图扫描。
3. **规划查询上下文与目标索引。** 减少同一状态反复建表、筛目标和计算事实。
4. **受控候选共享与复制边界收缩。** 在前面建立的安全边界上继续降低分配和GC压力。

每批完成时须保留世界结果、事件顺序、候选与路径决策、双随机序列、旧快照隔离及存档语义；未知Mod或脚本能力保留完整回退。使用项目已有正确性检查及必要的针对性回归支撑这些边界，不把本规划变成要求用户重复操作手机的测试流程。

目标是让后期局面的新增工作不再被全图搜索、反复扫描与深拷贝成倍放大。不能保证不同局面绝对等时，也不能在实施前承诺固定秒数。首批重点看真实搜索范围和扫描次数是否减少，随后再压缩分配；已完成的冻结规则、不可变地块复用及保存缓冲不列为新成果。
