# 两台手机本轮测试：性能分析与后续规划

日期：2026-10-24。范围：用户截图与后续计时整理、既有记录复核、当前源码只读检查、优化规划。**本轮仅维护本文档，不修改实现、配置、既有状态或日志，不运行性能实验，不构建或发布。** 文内方案不是实施授权；截图中的聊天建议仅作为待评估线索。

**最新补充：连续回合测试全部来自新手机iQOO Z11，斜杠两侧是两次测试序列，不是两台设备。第6回合前存档、退出清内存后重进，仍耗时37秒。详见第8节：调查优先级调整为后期局面/持久历史的工作量放大，缓存滞留仍保留为候选原因，尚未证实。** 第1–7节保留此前双机截图的独立数据，不将后续测试覆盖到老机上。

## 2. 相较上轮的改善及剩余差距

| 设备 | 上轮R版 | 本轮R版 | 绝对减少 | 报告值下降比例 |
| --- | ---: | ---: | ---: | ---: |
| Mate 30 Pro | 34.5秒 | 25.1秒 | 9.4秒 | 27.2% |
| iQOO Z11 | 25.6秒 | 约19秒 | 约6.6秒 | 约25.8% |

两台设备均出现约四分之一的耗时下降，方向一致，支持近期整批改动有效的判断；不能把收益全部归因于Pixi、搜索或某一次冻结优化。上轮与本轮不是交替重复实验，实际开局随机数也未固定。

老机原版也由6.4秒变成5.6秒，下降12.5%，说明测试条件或局面执行存在波动。老机R/原版倍率由5.39降至4.48，倍率下降约16.9%；这是补充观察，不能当作扣除硬件波动后的严格净收益。新机上轮没有原版计时，不能补算上轮倍率。旧“手机下降30%”目标尚不能宣布完成。

本轮老/新手机的过回合耗时之比，R版约1.32，原版约1.39；R/原版倍率则分别为4.48和4.70，接近。这提示两机可能承担相似的额外工作或执行开销，值得继续优化共用路径；**仅凭两个计时点不能区分CPU计算、GC、运行时、存储或前后端调度，更不能据此认定某一项占比。**

进图表现不同：R版老/新机相差约4.62倍，而原版均报告约1秒。应把“老机进图12秒”列为独立问题。截图没有同机上一版进图数值，因而只能说当前较原版慢、用户体感变慢，不能量化近期版本的加载回退。

## 3. 进图与过回合不是同一条优化链

### 3.1 当前进图关键路径：只读核查

| 位置 | 当前行为 | 对分析的意义 |
| --- | --- | --- |
| `rewrite/Ew4.Web/wwwroot/app.js`，选国流程 | 请求countries并加载strategicmap图集 | 已有战略图加载，但尚不是战场资源的完整提前准备 |
| 同文件，`start` | 在加载遮罩中等待`rpc('start')`，再执行`installState(..., true)` | 后端开局与前端后续准备处于串行依赖链 |
| `rewrite/Ew4.Client/ClientGame.cs`，`Start` | 创建/结算对局，存账户、更新当前游戏、重置历史、自动保存并生成视图 | 进图包含后端与持久化工作，不只是绘图 |
| `rewrite/Ew4.Client/ClientContent.cs`，`Start` | 创建世界时抽取战斗/AI随机种子，装配规则与场景 | 正式开局不能随意提前调用或反复丢弃 |
| `app.js`，`installState` | 等待本局兵种及常用特效图集；开局等待地图tiles列表、普通/高清地形和建筑等图片，再等待`battlefield.prewarm` | 解码、资源范围和模板生成都可能进入加载等待，需要分别量化 |
| `rewrite/Ew4.Web/wwwroot/battlefield.js`，`prewarm` | 新建Surface，扫描扩展视口内格子，生成海岸/边界模板，约每4ms检查让出执行 | 这是CPU模板预热；4ms是协作检查阈值，单个昂贵模板仍可能超过它 |
| 同文件，`scheduleChunkWarm` | 在战场绘制后的空闲时段生成远景/视口块，并分时上传GPU | 与上述阻塞进图的模板预热不同，不能把12秒全算在新增远景预热上 |
| `app.js`，`withLoading` | 至少显示约700ms，并让出两次动画帧 | 700ms是最低总显示时间，不是每次额外加700ms；长任务通常已覆盖下限，不能解释12秒 |

当前`prewarm`扩展矩形按画布尺寸除以0.48并加边距计算；它是否超过实际首屏所需、产生多少模板及淘汰，值得测量。当前每次进入都新建Surface，已有模板不能直接据此保证跨次进图复用。海岸模板缓存有512项上限，是否出现预热阶段先生成后淘汰仍待计数，不能作为已发现故障。

图像已有按路径缓存，图集成功加载后也有缓存，因此不应重新设计一套重复缓存。`loadLibrary`目前在完成后登记结果，若以后让选国预加载和正式加载重叠，应合并进行中的同名Promise，失败可重试，避免新增重复请求和解码。

Android资源请求经本地WebView拦截读取APK/Mod资源，并非公网下载。资源字节读取、解码、运行时首用、后端创建和存储均是候选因素；`no-store`不等于前端内存缓存失效，也不能直接证明瓶颈。

### 3.2 过回合当前仍有明确的后端工作量

据[最近已实施批次](TURN_NEXT_IMPLEMENTATION_20261024.md)，搜索容器改写、战术规则冻结和作用域边界修正已经完成；不能把旧规划中的这些项目再次列为未做。

最近保存的征服1诊断记录仍有：

- 完整世界校验3535次，其中候选1867、执行771、提交572、规划306、保存19；候选约占次数的52.8%，这不是时间占比。
- 完整校验累计访问约1899万格和90万单位；保持了原正确性检查，并未完成候选增量校验。
- 桌面未注入热样本累计分配约2556 MiB/轮。这是累计分配，不是手机峰值内存。
- 距离场缓存查询1764次、命中0；此前队列/容器优化已经降低搜索成本，尚未减少实际搜索工作量。
- 保存及强制flush仍19次。此前桌面探针证明它值得单列，但不能把桌面耗时当作手机存储耗时。

以上是既有批次证据，本轮未重跑。当前快进前端已走批处理和增量状态，常规中间批次主要应用状态并刷新进度；完整`installState`通常留在停止/错误边界。继续前端优化应围绕剩余数据、绘制和调度成本，不假定每个AI步骤都在播放完整动画。

**选国阶段的资源预热主要改善进图和首次镜头操作，不能直接消除完整世界校验、AI搜索及保存。** 不建议在选国页预演AI回合：玩家开局操作会改变状态，而且会增加取消、重算和随机序列一致性的成本。

## 4. 对“从选国开始预渲染”的评估

结论：**建议做有限、可取消、可复用的提前准备；优先提前资源读取/解码，再根据实际收益决定是否提前生成模板或地图块。** 不建议选国即渲染全图、全兵种动作或所有高清档。

| 阶段 | 推荐准备内容 | 限制 |
| --- | --- | --- |
| 进入某征服的选国页 | 当前地图公共图像、确实会用到的基础图集、必要字体；可安全复用的只读场景解析 | 按场景与资源版本去重；低优先级、限制并发；不能拖慢选国点击和滚动 |
| 国家稳定选定、用户仍停留 | 若可用只读预览确定初始镜头，准备首屏必要模板/小范围地图块 | 必须证明预览状态与正式开局一致；不能为此创建正式游戏或提前消耗随机数 |
| 点击开始 | 接管已完成或进行中的准备，仅等待正确首屏所必需的剩余工作 | 无需等全部远景/高清资源；0秒停留也必须正确加载 |
| 战场已可操作 | 分时补齐邻域、远景及确有需要的高清资源 | 输入、AI快进、页面切换优先；后台任务有取消与总预算 |

实施时应具备的边界：

1. **禁止用现有`/api/start`做预热。** 它会改变当前游戏、账户及自动存档，且会抽取随机种子。选国准备只读、无持久化副作用；有需求时单独设计预览入口。
2. 状态相关缓存区分场景、地图、国家/初始镜头、Mod资源版本、规则/配色、语言、密度与GPU上下文。公共图片可共享，含领土与建筑外观的块不能仅以地图ID复用。纹理或字体未就绪的块继续遵循失效规则。
3. 快速切换国家、返回菜单或切Mod时用任务代次淘汰过期结果；已发出的不可取消请求不能保证停止，但过期结果不得安装到当前场景。取消后释放无用对象。
4. 首批维持现有12 Mi像素地形块预算，并把提前准备占用计入同一预算；另行统计模板、图片、CPU/GPU副本与峰值。不能把预算外的选国缓存藏起来。老机不默认同时准备普通、高清两套可替代资源。
5. 普通资源若支持正确首屏，可先用普通清晰度，再补高清；必须检查显示正确、文字清楚、无缺图闪烁。这里是待验证方案，不代表当前可以直接删除高清等待。
6. 从真实低端设备成本调整切片粒度；“每次一块”仍可能产生长任务。先减范围、去重复和复用，只有确实必要时再评估更细切片/Worker，不能假定旧WebView支持所需OffscreenCanvas路径。
7. 已进入AI快进时暂停非必要远景预热，避免与计算、状态处理和存储争用；这是待实施调度方案，当前未证明已有该项优先级。

提前做工作不等于消除工作。如果只让用户在选国页多等，而完整进图流程不变，则只是等待位置转移。必须同时记录“点击开始至可操作”和固定停留条件下“进入选国页至可操作”，不能只展示前者。

## 5. 推荐后续批次与验收

以下是后续获得实施授权后的顺序，不在本轮执行。进图与过回合分别设目标、独立交付对照，避免一次混入全部变化后无法判断收益。

| 次序 | 工作 | 主要产出与验收 |
| --- | --- | --- |
| P0 | 冻结当前比较基线，复用桌面分组诊断；设计自动记录总耗时/构建标识 | 两机端到端结果可比较；细分手机遥测可选，不作为继续优化的前置条件 |
| P1-L | 进图关键路径分段；选国页有限资源预载；首屏等待范围与进行中加载去重 | 老机12秒问题有可归因改善；新机不回退；选国不卡，立即开始正确，重复进图确有复用 |
| P1-T | 推进候选校验A3的受控变更集，先覆盖可证明的内置路径 | 正确性等价前提下减少实际校验访问；未覆盖的事件、投降、外交、脚本继续完整校验 |
| P2-T1 | 保存编码/缓冲及世界复制分配分别做独立优化 | 保留保存边界、原子替换、flush及旧快照隔离；比较整轮时间、分配、GC与恢复正确性 |
| P2-T2 | 追踪距离场缓存键和复用距离，核查0命中原因 | 先判断键本身不重复、作用域过短还是8项清空策略影响；只有可复用证据成立才改缓存 |
| P2-A | 同源码AOT独立A/B | 核实实际AOT产物，测两机启动、进图、首轮/热轮、包体与内存；不承诺AOT能填平4.5倍差距 |

候选校验的难点已经明确：移动可能涉及行政区、盟国土地、投降及场景事件。需要受控写入覆盖这些关联约束；不能仅检查起终点、只少调用Validate，或用全图比较生成“增量”来伪装节省。首批保留实际选中动作提交后的完整校验，开发验证进行完整/增量双跑，性能计时不混入双跑。

若A3的安全覆盖成本过高，可先推进可独立验证的分配/保存编码优化，A3保留为独立工作。暂不同时重写世界结构、取消保存、扩大AI批次预算、削减AI候选或更换渲染库；这些措施不能用来替代等价优化。

工程验收建议：

- 首批以“同机重复样本中位数明显改善，另一台无可复现回退”为门槛；可将过回合再降低15%–20%、老机点击开始等待降低30%作为阶段目标，不是预测。若暂用本轮单点代入，20%过回合目标约为20.1/15.2秒、老机加载30%目标约为8.4秒；正式验收须改用新采集的对照中位数。
- 接近原版所需的剩余降幅仍很大：以本轮数值计，R版过回合需再减少约77.7%/78.7%才能接近5.6/4.04秒。不能承诺靠一轮预热或单个缓存修正达到。
- 长期目标仍是缩小原版差距，同时保证同一R版逻辑前后等价。原版与R版步数、AI选择及持久化实现未做完全等量证明，原版耗时用于用户体验参照，不要求优化后模仿原版决策。

## 6. 后续测试方案：保持用户操作简单

继续两台原设备、第一征服法国、不操作直接快进。征服4用于开发侧补充覆盖，不增加本轮用户工作。

**过回合：** 优化前后同一R版固定存档/双RNG起点，每版3–5次、交替分组；首轮和热轮分开。每次恢复同一起点，不把连续第2、第3回合当重复样本。主计时从点击结束回合到最终状态显示、控制权恢复。允许录屏或现有人工计时，不要求ADB和手机探针。自然新开局会抽取随机种子，现有用户单点仍可做趋势参照，但严格A/B应由开发侧准备固定起点。

**进图：** 分别测进程重启首次进入与同进程重复进入；先用当前相同协议重测对照。测试选国停留0秒、约2秒、约5秒，时间是控制实验条件，不是给玩家增加强制倒计时。分别记录选国页显示、点击开始、首个正确战场帧、真正可操作、立即缩放/拖图的体验。冷进程不等于清空OS磁盘缓存，不默认卸载清数据。

**开发侧可选分段：** 后端创建/校验/保存/视图；前端图片读取/解码、图集准备、模板预热、首次建块/GPU上传、首帧与控制权恢复。加载各段可能重叠，按时间线分析，不把并行耗时相加。JS与C#各用自己的单调时钟，不能跨时钟域直接相减；首帧回调仅为软件近似边界，可用录屏抽查。

**正确性及资源：** 保持两图逐步世界/事件、候选顺序、双RNG、步数及停止边界一致；加载优化另验快速切场景/国家、立即开始、Mod切换、语言/旋屏、旧WebView、Canvas回退和GPU上下文丢失。校验无串图、漏图、错误阵营色、额外写档、随机序列变化或失控增长的内存。保存相关改动另测崩溃、写入失败与恢复。

## 7. 结论与证据入口

本轮支持“近期优化有效，但差距仍大”：两机R版报告耗时较上轮下降约26%–27%，仍约为各自原版的4.5–4.7倍；进图的老机12秒问题值得独立优先处理。选国预载可以减少点击开始后的等待，但必须与首屏范围收缩、已有缓存复用配合；过回合主线继续是减少后端重复工作和分配，并保持持久化与规则正确性。

## 8. 连续回合变慢：新手机重复测试补充

### 8.1 数据更正与完整记录

用户随后明确：**本节全部是新手机iQOO Z11的反复测试成果**，R版两列是两次测试序列，不能标注为新机/老机。原版反复测试差距小于等于1秒，R版存在波动。本节来源为用户文字补充，未新增附件或本机测量。

| 连续回合 | 原版一组记录 | R版序列A（原左列） | R版序列B（原右列） |
| --- | ---: | ---: | ---: |
| 第1回合 | 4.24秒 | 19.16秒 | 22.15秒 |
| 第2回合 | 4.26秒 | 22.83秒 | 23.88秒 |
| 第3回合 | 4.33秒 | 24.18秒 | 25.01秒 |
| 第4回合 | 未提供 | 未测 | 27.77秒 |
| 第5回合 | 未提供 | 未测 | 33.49秒 |

另记：**第6回合过回合之前存档，退游戏清内存后重进，过回合37秒。** 用户未给出同一第6回合在不重进条件下的对照耗时；也未明确这一条归属A/B哪条序列，不擅自补入B列。保留“清内存”为用户操作描述，未通过设备工具验证进程退出、系统缓存或温度状态。

数值观察：

- 原版该组第1至第3回合只增加0.09秒，约2.1%；用户补充的“重复测试差距≤1秒”是另一项重复性描述，不能用这三个点算出全部样本的波动范围。
- R版A第1至第3回合增加5.02秒，约26.2%；B同期增加2.86秒，约12.9%。
- R版B第1至第5回合增加11.34秒，约51.2%。逐轮增量为1.73、1.13、2.76、5.72秒；后两步增幅变大，但只有五个点，不能据此拟合为线性、指数或无限增长。
- R版同编号回合跨两次测试差值分别为2.99、1.05、0.83秒。首回合波动较明显；两列不是相同存档/随机种子的严格重复实验，不能把全部差值归因于随机测量误差或温控。
- 第6回合重进后37秒，说明用户仍遭遇明显后期等待。它不是“重启使同一回合更慢”的证明，因为缺少同起点的不重启对照。

此前只用首回合筛选的验收不足以覆盖这类问题。后续必须增加连续回合曲线和固定后期存档测试，同时保留首回合基准。

### 8.2 对“不必要缓存过多”的判断

这个推测值得查，但现有证据不足以确认为根因。需要区分四种不同情况：

| 机制 | 为何可能越玩越慢 | 退出重进后的预期 |
| --- | --- | --- |
| 进程内对象/纹理滞留，GC或内存压力增加 | 旧数据仍被引用、缓存容量或对象数增长 | 真正退出通常会释放这些对象；但首次运行重建缓存/JIT会有额外成本 |
| 随存档保存的历史或状态增长 | 每次复制、全量校验、查询和序列化都处理更多数据 | 读档会恢复这些数据，重进后仍可能慢 |
| 后续局面的AI工作量增长 | 新兵、可行动单位、交战目标、移动候选或搜索量变化 | 同一局面重进仍需要这些工作；单位总数不增也可能更复杂 |
| 设备运行条件变化 | 温升降频、后台负载、存储延迟或GC时机 | 重进不必然冷却设备；清内存也可能使资源重新加载 |

**37秒结果使“仅靠清空易失缓存就能恢复首回合速度”的假设不再是首选，但不能单独排除内存滞留。** 冷路径成本可能掩盖释放内存的收益；后续需要同一第6回合起点、同温度与预热条件的配对比较。

原版较稳定，是R版后期成本需要治理的重要体验证据，但两者AI决策与状态实现未证明完全相同，不能据原版稳定就排除R版AI工作量变化。

### 8.3 源码只读核查：哪些已有限制，哪些确实可能累积

以下是当前工作区静态事实，不等于已在手机定位到耗时来源；测试包与工作区的精确一致性未在本轮核验。

| 对象/路径 | 实际实现 | 当前判断 |
| --- | --- | --- |
| 战略距离场，`WorldAiStrategy.cs` | 每次战略规划中的局部字典，单个运输选择分支内创建，达到8项清空 | 不是每轮不断追加的全局距离缓存；可以产生重复计算和分配，但暂不支持它跨回合滞留的推断 |
| 动态校验证明，`PlanningScope.cs` | 同步作用域内集合，`using`退出后恢复上层；顶层结束不再由current持有 | 当前入口不是永久累积世界快照的证明缓存；仍需实际对象保留证据才能排除其他引用 |
| 冻结模板/规则证书 | `ConditionalWeakTable`按对象身份登记 | 采用弱键设计，不应直接当作强引用无上限缓存；不能据此证明整个运行时没有泄漏 |
| 撤回记录，`MovementHistory.cs` | `Observe`在回合或势力变化时Reset，清除移动和攻击者记录 | 不是将每一轮撤回历史永久串在一起；其设计不支持跨轮不断增长的猜测 |
| 地形块/模板/兵模/标签 | 地形块12 Mi像素预算，海岸模板512项；兵模姿态1024项或画布8 Mi像素，地图文字96项、城市文字1024项、血条256项 | 多处已有上限，但不是总进程内存上限；当前可见块受保护，资源副本/键数与淘汰抖动仍须核查 |
| Pixi资源，`pixi-battle.js` | 源纹理像素超过48 Mi时淘汰非本帧来源至40 Mi；每来源有frames映射，绘制对象池按历史峰值复用 | 像素预算未直接限制frames元数据或对象池数量；对象池尾部每帧隐藏扫描，历史峰值和引用值得计数，尚未证实异常增长 |
| 前端图片/图集、朝向记录，`app.js` | 图片/图集按资源路径驻留；`facings`按单位ID登记，本次检索未见对它的clear/delete | 有生命周期审计价值。固定资源集合会趋于稳定，按单位ID的项可能增长；快进绕过大量普通动画更新，不能直接认定朝向记录导致数十秒等待 |
| 死亡与事件历史，`WorldDeaths.cs`、`WorldState.cs` | 每次单位死亡将ID追加去重到`DestroyedScenarioUnits`，将领死亡有独立列表；世界复制会复制这些历史 | 这是明确存在的随对局增长路径，值得优先测数量和重复处理成本；记录本身属于游戏状态，不能直接删除 |

最值得优先验证的具体链路：

1. `WorldDeaths.Remove`对每次死亡执行`Append(...).Distinct(...).ToArray()`，死亡历史会增长。不是保存一份完整死兵对象，但会保留ID并重复生成集合。
2. `WorldState.Copy`会复制死亡列表、已触发事件、选择及事件进度等集合。活着的单位减少不等于总世界复制成本下降。
3. `ScenarioRules.Validate`在判断“没有场景事件可直接返回”之前，就会对死亡历史做空值与重复检查（`Any`、`Distinct().Count()`）。因此即使场景事件为空，这项扫描仍存在；`WorldState`的完整校验会调用该验证。
4. `ClientGame.Save`经`SessionSave.Encode`、`WorldSave`编码世界，然后写入临时文件并强制flush、原子替换。死亡及事件历史作为世界状态被保存，重进后仍会读回。

这说明存在“持久历史增长 × 重复处理次数”的成本放大机制，但**没有测到第1至第6回合这些集合的实际数量与时间，不能宣称它解释了11秒或37秒。** 几十个ID的单次扫描通常不大，真正要核查的是它被重复了多少次、是否伴随其他全世界复制/分配。

死亡历史供`unit_destroyed`、`commander_dead`条件查询，事件进度还关系到剧情和重复触发。后续若优化，应优先考虑不可变集合安全共享、受控写入边界校验、查询索引和编码复用；只有证明全部规则、脚本、读档及Mod契约不需要某项记录后，才讨论裁剪。不能按“没有当前可见用途”直接清空。

### 8.4 更新后的定位顺序

本节补充第5节P0的优先内容：先查清后期变慢由什么增长驱动，再决定候选增量校验、历史结构、缓存生命周期或搜索优化的先后。选国预热继续属于加载问题，不能用来解释或解决这条连续回合曲线。

**第一步：固定后期起点并统计工作量。** 后续实施时保留同一对局第1、3、5、6回合结束按钮点击前的测试存档及双RNG，不用重新开局得到不同局面代替。每轮同时记录活跃单位、新招募/死亡数量、有效势力、AI步数、候选数、搜索访问量、校验访问量、复制次数、历史集合长度、保存次数/字节数。先比较“工作变多”还是“同等工作越来越慢”；每步耗时只作辅助，因为不同步骤的成本不同。

**第二步：用相同第6回合存档区分局面与进程。** 开发侧建立两组：已经连续运行多轮的进程，以及新启动进程；两组都恢复完全相同的第6回合起点，配对比较首次与合理预热后的样本。预热在隔离副本进行，计时前重新恢复起点，保持随机序列、输入状态、画面设置和设备温度条件一致。不能把新进程首次冷运行直接与老进程热运行归因比较。重进可能清掉内存状态但不能清掉存档历史，正好可帮助区分两者。

**第三步：补交叉测试。** 长时间运行后恢复固定第1回合起点，如果首回合也变慢，再看冷却后是否恢复；如果第1回合仍快、第6回合在新旧进程均慢，更支持局面/持久状态成本。读档也可能重置部分缓存，因此该实验只是证据之一，必须结合对象保留和工作量统计，不能用一次重读档下唯一结论。

**第四步：记录实际内存趋势。** 分开采集累计分配、自然GC后的存活托管堆、GC次数/暂停、JS堆、WebView/原生内存、纹理像素/条目/frames数、绘制池峰值与命中/淘汰/重建次数。累计分配几GiB不代表有几GiB缓存滞留；系统PSS不下降也可能是运行时保留可复用内存，不能直接认定泄漏。对象引用分析或强制GC只能放独立诊断，不能改变主性能样本。

按证据选择实施方向：

| 后续发现 | 优先处理 |
| --- | --- |
| AI步数/候选/搜索访问明显增加，存活内存稳定 | 降低每单位/每候选的重复工作，复用同快照查询；不通过减弱AI掩盖问题 |
| 历史长度及其复制/校验/编码独占时间增长，重进不恢复 | 优化持久历史的数据结构与处理边界，保留事件语义及存档兼容 |
| 同一固定局面在老进程更慢，存活对象或元数据持续增长 | 定位保留引用和生命周期，修具体淘汰/释放，不“一回合清光所有缓存” |
| 缓存容量稳定但命中低、淘汰和重建激增 | 修缓存键、依赖失效与预算分配；清缓存可能进一步恶化 |
| 工作量和内存相近，冷却后明显改善 | 调整CPU/GPU峰值、后台预热争用与持续负载，单列温控影响 |
| 主要是重进后的第一次慢，后续恢复 | 另列JIT/资源/缓存重建冷路径；不能把冷启动成本当成持续泄漏 |

### 8.5 连续回合验收边界

后续优化至少保留现有第1–6回合的完整曲线，开发侧可扩展到10–20回合筛查长期趋势；手机仍允许只提供整轮计时，细分诊断由开发侧承担，不增加必须连接电脑或手动采集内存的门槛。

前后版本比较必须使用对应的同一存档/RNG，保持逐步规则等价，并逐轮列出耗时、工作量、历史规模、分配和存活内存。目标是控制不必要的跨轮增长与重复成本，不要求不同局面的每一轮绝对相同耗时；也不以首回合提速掩盖后期回退。不得把“清缓存”“重进”或“强制GC后看起来变快”本身当作最终解决方案。

当前结论：**连续回合变慢已由用户两次序列支持，根因未定；退出清内存后的37秒反馈，使持久状态/局面工作量及其重复处理优先于“纯进程内缓存堆积”接受验证。** 本次追加仍仅为静态分析及规划，没有改代码或运行新的性能实验。
