# 视觉小说式剧情呈现接口规划

日期：2026-10-27。首版已按参考图接入源码及独立演示；实际字段、限制和示例以[已实现接口](mod-kit/docs/porting/STORY_PRESENTATION.md)及[实现记录](STORY_PRESENTATION_IMPLEMENTATION_20261027.md)为准，本文保留设计背景与后续范围，不表示所有拟议字段均已实现。未打包或正式发行。

视觉已根据用户反馈修订：参考图 5／6 的历史题材对话结构、图 1–4 的紧凑工具与历史／设置；底部对话区贴住左右边和底边，取消外边距／装饰边框；工具默认无底框，自动使用“播放图标＋自动”，其他以图标及倍速数字表示。开局／事件／局末共用同一播放器。

## 1. 目标与第一版范围

进入配置了剧情的关卡后，显示全屏背景、多个人物立绘、人物名称和对话框。点击推进台词，可以同时换背景、换人物表情或动作、进退场及播放基础动画。提供手动、自动、倍速和整段跳过，电脑与 Android 使用同一套资源和脚本。

第一版支持线性及分支演出、旁白、多人同屏、整图与分层立绘、背景切换、平移／跳动／淡入淡出、说话人明暗、历史文本、隐藏对话框及播放设置。播放器有“开局调用”“作为事件结果调用”和“局末调用”三类入口；剧情的开始、完成、所选选项和结局可作为事件条件。剧情内部直接显示多个对话选项，复用已有条件与结果规则，选项能够改变剧情路线及游戏状态。局末按不同胜利结局／特殊失败结局选择剧情，固定先播放再显示结算窗口。配音、口型同步、Live2D／骨骼和可视化编辑器列为后续扩展。

界面以用户提供的六张参考图及上述最新反馈为依据。下文未经实现说明确认的尺寸、字段及扩展能力仍为设计建议。

## 2. 当前工程接入依据

- `Ew4.Web/wwwroot` 是共享前端；Android 使用 WebView，适合增加独立剧情舞台模块，由两端共同使用。
- `Ew4.Client/ClientGame.cs` 已投影对白、关卡介绍和事件选择；`Ew4.Core` 已用 `PendingDialogue`／`QueuedDialogues` 阻塞战局和 AI，存档也已有这些状态。新增剧情需要接入共同等待机制，不能仅显示一层前端遮罩。
- `Ew4.Core/ScenarioRules.cs` 已有条件事件、弹窗选择和结果事务，可增加剧情引用与完成确认，复用触发条件。
- 已有 `ending` 结果保存胜利／失败及 `ScenarioEnding` 分支 ID。`Ew4.Client/ClientSettlement.cs` 会处理战役进度与结算，`victory-ui.js` 会等待旧对白／弹窗后显示结果；局末剧情需同时接入后端结算门槛和前端显示门槛，不能仅增加播放遮罩。
- 内置扩展在 `data/rewrite/`，APK 会打入 `assets/rewrite/`；Mod 导入也识别 `rewrite/`。适合统一收纳剧情脚本和媒体。
- 当前 `Ew4.Mods/ModFiles.cs` 对 `rewrite/` 只允许 JSON、Lua、PNG。若开放 WebP、JPG、音频，必须同步修改导入白名单、文件校验、HTTP／WebView MIME 和资源清单，不能仅复制文件。

以上是现有能力；下文的新字段、模块名和目录均为拟议设计，不是当前可调用 API。

## 3. 屏幕与操作

舞台由后到前排列：背景 → 背景过渡 → 人物容器 → 场景淡幕／闪光 → 姓名与对话框 → 播放工具与历史面板。允许隐藏文本查看完整场景。

- 背景铺满舞台，素材可配置焦点和完整显示／裁切方式，避免超宽屏把重要主体裁掉。
- 人物按脚底／半身底边锚点定位，提供左、中左、中、中右、右预设，也支持归一化坐标、缩放、镜像、前后顺序。常见 2 至 4 人构图可直接使用，数量不写死为两人。
- 说话角色正常亮度，其他在场角色默认约 60% 亮度，切换时短渐变。姓名栏通过角色 ID 绑定；旁白、画外音、匿名角色允许独立名称，不要求存在可见立绘。
- 下方对话框按视口设置稳定区域，姓名和正文分离；长台词支持分页，保留所有文本，不让按钮挤压正文。留出下一句标记与触摸区域。
- 姓名、正文和必要图片就绪后一起显示；切句只更新变化部分，异步加载结果要核对当前剧情／步骤版本，避免旧表情或旧台词覆盖新状态。

| 操作 | 拟定行为 |
| --- | --- |
| 点击舞台／正文 | 正在逐字显示时补全本句；本句完整时推进下一句。可配置整句直接显示 |
| 自动 | 按文本长度等待后推进，可随时暂停；手动推进后重新计时 |
| 速度 | 1×、2×、4×、8×；缩短文字、等待和过渡时长，极短动画直接落到终态 |
| 跳过 | 无待选分支时跳到下一选择节点或剧情结束；在选择处停下，选择后可再次跳过；采用一次独立点击而非长按 |
| 对话选项 | 在剧情舞台内显示多个选项，单次择一；支持连续多个选择节点、可用条件和选择结果 |
| 历史 | 查看本段已读姓名与台词，打开时暂停自动；查看历史不重新执行演出或游戏结果 |
| 隐藏文本 | 隐藏对话框与工具后查看场景，再次点击恢复；隐藏期间暂停推进 |

“自动”决定是否自行推进，“速度”决定推进节奏，两者独立。初版自动阅读等待可按 `max(0.8 秒, 0.8 秒 + 字数 × 0.06 秒) / 倍速` 估算，最终经手机阅读实测调整。默认只在台词、必要过渡完成后开始阅读等待。

全局可记忆自动播放与速度；另提供“进入关卡时跳过剧情”设置，初始关闭。已读记录用于标记与重看，不默认强制跳过首次剧情。第一版即支持选择节点，自动、倍速、手动点击正文及任何跳过设置都不能代选。无选择的整段可直接结束；存在选择时按已确定路线跳到下一处待选节点，玩家选择后才能继续，不能执行未走分支的结果。已有有效选择的读档恢复按已提交记录继续，不再询问或重复结算。

选项出现时保留背景、人物及当前对话，可根据参考图决定选项居中或靠近对话框；选项区独立滚动，支持长文字及手机触摸。条件不满足的选项默认禁用并可说明原因，也可配置隐藏。进入节点必须至少有一个可用选项；提交时后端重新检查条件与资源，失败留在当前节点并刷新选项，不扣资源、不推进。

按钮点击不能冒泡为下一句；一次触摸只执行一个操作。切后台、系统弹窗、历史、设置及资源加载暂停计时，返回后继续，不按离开时长追赶播放。Android 返回键先关闭剧情内面板，再暂停演出并进入现有返回流程。

## 4. 资源组织与复用

建议单独使用以下目录，使用稳定 ID 引用资源，同一背景、人物和表情可以被多关调用：

```text
rewrite/data/rewrite/story/
  catalog.json
  backgrounds/
    command_room.png
  characters/
    officer_a/
      character.json
      standing/body.png
      standing/face_neutral.png
      standing/face_serious.png
      standing/arm_point.png
      seated/full_neutral.png
  scenes/
    campaign_opening.json
  texts/
    zh-CN.json
  ui/
    dialogue_frame.png
```

对应 APK 为 `assets/rewrite/story/`，Windows 发布目录为 `data/rewrite/story/`，Mod 包为 `rewrite/story/`。应用层通过资源 ID 及统一解析器访问，不在剧情文本中写平台绝对路径。注册入口拟在 `rewrite/extension.json` 中增加 `storyPresentation`，指向 `rewrite/story/catalog.json`；具体 API 版本实施时确定。

文本支持直接中文，也支持文字键；长篇内容推荐文字键＋独立语言文件。可先用 PNG 保持现有兼容；大背景后续支持 JPG／WebP 压缩，透明分层用 PNG 或带透明通道的 WebP。PSD 等制作源留在创作目录，运行包只放导出素材。

角色定义与将领定义分开：历史人物、虚构人物和普通士兵都能创建角色，按需关联 `commanderDefinitionId`，无需先创建战斗将领。角色定义默认姓名，台词可以临时使用“？？？”等显示名。

## 5. 立绘拆分与基础演出

同时允许两种素材方式，并允许同一角色按姿势混用：

1. 整图：按“姿势／表情”直接替换一张完整透明立绘，适合先快速接入已有素材。
2. 分层：角色按姿势定义底图、脸、眼、嘴、手势、配件等图层；每层有默认部件、绘制顺序、偏移和互斥分组。换表情仅替换脸／眼／嘴，换动作则切换姿势及该姿势允许的部件。

每个姿势定义统一参考画布、锚点及部件坐标。推荐各图层导出为同尺寸透明画布；如需裁切节省空间，必须保存裁切前原点和偏移。不同动作的脸不保证通用，用姿势内映射校验，禁止错误叠到身体上。坐姿、背身或大幅动作可直接使用独立整图。

舞台位置与人物动作采用独立容器：外层负责站位／进退场，内层负责跳动／摇动，图层负责换装与表情，避免多个动画争用同一个 transform。

第一版演出指令：显示／隐藏、移动、缩放、镜像、换姿势／部件、淡入淡出、短跳、轻摇、背景切换。每条动画可配持续时间、缓动、位移和是否等待；允许多人同时动作。少量固定预设即可满足起步演出，不开放任意网页代码。

同一角色属性上的新动画应替换或排队，规则固定。手动推进、跳过、关闭和读档都能取消动画并落到明确终态；装饰性循环不阻塞阅读和结束。表情／说话人的亮度应用在整个角色容器上，保证拆分层表现一致。

## 6. 剧情脚本接口草案

使用带 schema 版本的 JSON，并用现有结构化解析和校验链加载。脚本由稳定步骤 ID 串联：进入某一步时可设置背景、改变在场人物、播放动画并显示本句。人物状态沿用到下一步，未提及的角色不退场；提供明确的清场指令。

以下仅示意作者表达方式，字段尚未冻结：

```json
{
  "schema": 1,
  "id": "campaign.opening",
  "steps": [
    {
      "id": "briefing",
      "background": "command_room",
      "actors": [
        {"id": "a", "character": "officer_a", "slot": "left", "pose": "standing", "expression": "serious"},
        {"id": "b", "character": "officer_b", "slot": "right", "pose": "standing", "expression": "neutral"}
      ],
      "speaker": "a",
      "textKey": "opening.001"
    },
    {
      "id": "reply",
      "updateActors": [{"id": "b", "expression": "surprised"}],
      "animations": [{"actor": "b", "type": "hop", "durationMs": 240, "amplitude": 12}],
      "speaker": "b",
      "textKey": "opening.002"
    }
  ]
}
```

这里的 `a`／`b` 是本场景人物实例 ID，角色素材 ID 与实例 ID 分离，允许相同素材扮演多个在场人物。无文本的步骤可以表示转场或等待，并自动前进。普通步骤默认连接数组下一步，也可用 `next` 跳转；带 `choices` 的步骤必须等待选择，不能按数组顺序穿过。第一版采用有向无环分支图，校验缺失引用、重复 ID、循环及无法到达合法结束的路径。

### 6.1 剧情内多选项事件

“多个选项”指每个节点提供多个按钮，由玩家选择一个；一段剧情可以有多个选择节点。每个选项有稳定 ID、显示文本、可选条件、结果列表和目标步骤；条件／结果复用 `ScenarioCondition`／`ScenarioEffect`，不另造一套资源和外交规则。

例如在军议中选择进攻、防守或继续讨论，选择既能改变后续台词，也能设置事件变量或支付资源：

```json
{
  "schema": 1,
  "id": "war_council",
  "steps": [
    {
      "id": "decision",
      "speaker": "a",
      "text": "下一步如何行动？",
      "choices": [
        {
          "id": "attack",
          "text": "拨款进攻",
          "condition": {"type": "money", "compare": "ge", "value": 200},
          "effects": [{"type": "money", "value": -200}],
          "next": "attack_reply"
        },
        {"id": "defend", "text": "固守阵地", "next": "defend_reply"},
        {"id": "discuss", "text": "先商议补给", "next": "supply_question"}
      ]
    },
    {"id": "attack_reply", "speaker": "b", "text": "立即准备进攻。", "next": "attack_end"},
    {"id": "attack_end", "end": true, "result": "attack"},
    {"id": "defend_reply", "speaker": "b", "text": "优先巩固防线。", "next": "defend_end"},
    {"id": "defend_end", "end": true, "result": "defend"},
    {
      "id": "supply_question",
      "speaker": "b",
      "text": "需要征集粮草吗？",
      "choices": [
        {"id": "collect", "text": "准备征粮", "next": "supply_end"},
        {"id": "hold", "text": "暂不征粮", "next": "defend_reply"}
      ]
    },
    {"id": "supply_end", "end": true, "result": "supply"}
  ]
}
```

此片段沿用前文的在场人物实例，完整场景需定义或显示 `a`／`b`。选择提交以“剧情调用实例＋节点 ID＋当前修订号”为依据，把选择记录、选项结果及下个步骤一次性提交；同一实例的同一节点只生效一次。普通翻页、历史查看和读档不能重新执行选项结果。

选项结果可以修改资源、变量、外交、势力、胜负规则等已有能力。简单结果可直接写入选项 `effects`；较复杂流程推荐记录 `story_choice` 或结局 `story_result`，让后续事件按条件执行。两种方式不能为同一奖励重复配置。终点 `result` 是可查询的路线结果，不自动等同于战役胜负；需要结束战役时显式使用已有胜负结果。

## 7. 关卡触发、跳过与存档

### 7.1 三类调用入口

三类入口共用同一个播放器、素材库、脚本格式及存档协议，差别只在调用时机：

| 入口 | 配置及语义 |
| --- | --- |
| 开局调用 | 在关卡绑定中配置 `openingStory`，带稳定调用键 `key` 和场景 ID `scene`；新开本局时执行，普通读档不再次创建调用 |
| 事件结果调用 | 在事件或原有弹窗选项的 `effects` 中增加 `play_story`，带 `key` 和 `scene`；事件条件满足或选中按钮后调用 |
| 局末调用 | 在关卡的 `endingStories` 中按胜负、结局 ID／目标原因绑定场景；先满足胜利／特殊失败目标，再播放对应剧情，完成后进入结算 |

示意开局绑定条目：`{"scenario":"conquest1","openingStory":{"key":"opening","scene":"campaign.opening"}}`。事件结果示意：`{"type":"play_story","key":"council","scene":"war_council"}`。同一场景可以由不同关卡、事件及选项复用；`key` 区分调用用途，不能仅凭素材场景 ID 混合完成记录。

例如“第3回合触发军议 → 播放剧情 → 玩家选进攻／防守 → 对应后续事件执行”，或“旧弹窗选中交涉 → `play_story` → 剧情里再选方案”。回合、占城、将领生死等触发条件仍写在原事件体系中。

每次调用有独立实例 ID，记录来源事件、来源发生次数、调用键和场景。重复事件每轮可创建新实例；同一次触发的重发、读档和连点不得重复创建。同一时刻只播放一段，其余按稳定顺序排队。

### 7.2 剧情作为事件条件

条件查询读取本局后端存档，不能使用前端“看过”偏好作为依据。拟增加：

| 条件 | 含义 |
| --- | --- |
| `story_started` | 指定调用键已经真正进入播放器；仅排队不算开始 |
| `story_completed` | 指定调用实例已到合法终点，必要选择全部提交，结束结果成功结算 |
| `story_choice` | 指定调用中的某个节点已选择指定选项，可以在剧情尚未结束时成立 |
| `story_result` | 指定调用已经完成，并返回指定结局／路线标签 |
| `story_count` | 指定调用键已成功完成的次数，支持 `eq/ge` 等原有比较运算 |

这些条件与已有 `all`／`any`／`not`、回合、资源等条件自由组合。选择条件示意：`{"type":"story_choice","key":"council","node":"decision","choice":"attack"}`；完成条件示意：`{"type":"story_completed","key":"council"}`；结局条件示意：`{"type":"story_result","key":"council","result":"attack"}`。

除累计次数外，默认查询该调用键最近创建的实例；新实例排队／播放时，不沿用上一次完成或选择。需要“本局曾经选择过”时显式使用历史查询范围 `scope:"any"`；同一次流程的精确关联由来源事件发生次数／实例 ID 绑定。不存在的记录条件为假，历史重看不新增完成次数。

选择结果原子提交后即可供条件查询，但外部事件链在当前剧情结束／释放等待时统一重评，避免台词中途插入其他弹窗。剧情内部需要立即分流时使用该选项的 `next`。完成后先写入完成记录，再重评事件链，之后才恢复玩家／AI 行动，避免错过下一段剧情；已进入局末流程时只处理指定的局末结果／续段，不能重启普通事件链或恢复战局。

### 7.3 结果执行顺序与事件完成

事件结果序列遇到 `play_story` 时，先执行其前面的结果并登记剧情及剩余结果的续接点，再暂停；剧情结束后继续后面的结果。例如“扣费 → 播放军议 → 发补给”，扣费只发生一次，补给只在军议完成后执行。开始前已提交的结果不因后续读档重做；当前选择及完成阶段各自以事务保证不出现半次提交。

新增剧情调用的事件，需要区分“已触发／已入队”和“已完成”。`event_completed` 只有在本次调用的剧情及剩余结果全部成功结束后才为真；原无剧情事件的语义保持。失败重试从当前续接点继续，不重新扣费。一个事件调用多个剧情时按结果顺序串行，前一个完成才进入下一个。

剧情选项若要调用另一段剧情，可把 `play_story` 作为选项的最后一个结果：先记录选择和其他结果，后继剧情排队到当前剧情结束后播放；依赖后继完成的结果放到其完成条件事件中。首版不在当前舞台内递归打开第二个播放器，校验相互调用循环，并为运行时事件链设置推进预算，超限暂停并给出来源定位。

选项或续接结果改变战役胜负时，先完整提交本次原子结果组，锁定终局并停止新增普通行动／事件；当前剧情完成既定结尾后，进入绑定的局末剧情，最后结算。终局期间只接受当前剧情的有效推进／选择等命令，拒绝重复选择及战局动作。尚未执行的普通队列／事件续接不再启动；必须执行的收尾需明确配置为局末完成结果，不能依赖普通事件重新评估。

### 7.4 调度、跳过与恢复

开场顺序建议为：关卡载入 → 现有关卡介绍（可由配置选择保留或替换）→ 开场剧情 → 已排队事件／教程 → 允许玩家或 AI 行动。所有弹窗、旧对白和新剧情经过统一调度，避免重叠抢焦点；胜负已确定时按明确的结尾顺序处理，不能提前结算吞掉剧情。

- 后端负责触发资格、待播队列、当前场景／步骤、选项条件及已选记录、路线、完成标记和游戏结果；前端负责图片、文字、动画、计时与工具界面。
- 播放中复用统一等待状态，阻止点击地图、过回合、玩家 AI 和普通 AI 推进；后端同样拒绝这些操作。
- 新增剧情开始／推进／选择／完成／跳过命令，带场景实例和预期步骤版本；连点、旧响应、重发均不能越步或重复执行。纯演出状态不消耗战斗随机数，跳过也不额外抽取随机结果。
- 剧情图文与动画仅描述呈现，选择结果引用现有事件结果类型，由后端校验提交。明确区分开始前、选择时和结束后的结果；选择阶段和结束阶段分别原子提交，失败可重试。
- 跳过在后端沿已确定路线定位下一选择或合法终点，必要选择未经确认时不能伪造完成。不逐句请求、不重播动画、不执行未选路线的结果；到终点才走统一完成事务，排队剧情分别处理。
- 保存场景实例及调用键、来源事件／发生次数、脚本版本、稳定步骤 ID、各节点已选项、路线结果、事件续接位置和完成／已触发信息。图层状态从步骤快照或确定性重放还原，重建呈现不执行结果，不存 DOM 或动画时间。恢复到本句完整显示和动作终态；待选节点恢复待选，已提交选择恢复到后续步骤，之后等待点击，避免加载后立即自动跳走。
- 已读与自动速度是账户／设备偏好；决定事件能否重触发的标记必须在战局存档。重看只播放呈现，不执行游戏结果。
- 步骤推进更新内存状态，落盘可合并，但应用退出／后台前处理保存；不能为每个字或动画帧写存档。旧档按无待播剧情兼容，新 Mod 脚本变更按版本和步骤映射检查，不能静默重放奖励。

本地多人下，剧情面向谁显示、何时切换玩家及谁能推进，需要复用当前控制权规则；先确保不会在换人遮罩下泄露其他玩家信息。

### 7.5 局末剧情与结算顺序

局末流程固定为：**满足胜利／特殊失败目标 → 按现有规则裁决并锁定胜负及结局 → 调用相应剧情播放器 → 剧情完成 → 一次性结算 → 弹出结算窗口**。剧情可以包含前述选项，但窗口不能提前出现，也不能在播放中恢复地图操作或过回合。

拟在关卡绑定中增加 `endingStories`，例如：

```json
{
  "scenario": "conquest1",
  "endingStories": [
    {"key": "ending.perfect", "outcome": "victory", "ending": "victory.perfect", "scene": "endings.perfect"},
    {"key": "ending.negotiated", "outcome": "victory", "ending": "victory.negotiated", "scene": "endings.negotiated"},
    {"key": "ending.commander_lost", "outcome": "defeat", "ending": "failure.commander_lost", "scene": "endings.commander_lost"},
    {"key": "ending.victory_default", "outcome": "victory", "scene": "endings.victory_default"},
    {"key": "ending.defeat_default", "outcome": "defeat", "scene": "endings.defeat_default"}
  ]
}
```

以上仍为规划字段。`ending` 对应本局确定的结局 ID，可复用已有 `ending` 事件结果；不同胜利／特殊失败目标需要有稳定原因 ID，并显式映射到结局 ID。普通胜负没有分支 ID 时使用该胜负的默认剧情。结局展示文案不充当 ID，播放器脚本的路线 `result` 也不自动改写战役结局。

- 先按原有胜负优先规则处理同时满足的胜利／失败目标，再选剧情。精确结局绑定优先于对应胜负的默认绑定；同一结局只能有一个入口，多段收尾由该入口明确串联，不能因两个目标同时满足而重复播放。多目标映射到不同结局时要求明确配置优先顺序，不依赖遍历偶然顺序。
- 用本局 `BattleId` 和终局记录建立唯一局末调用实例；锁定结局 ID、胜负、触发原因、最终回合及结算所需数据快照。播放中的选项可影响结尾台词及明确配置的剧情变量／后继呈现，不能撤销锁定胜负、改判另一战役结局或再次触发局末入口。影响最终胜负的选择应放在终局判定之前的事件剧情中。
- 使用独立、可保存的局末阶段：待播／播放中／剧情已完成待结算／已结算。世界战斗阶段即使已经是 `Finished`，也必须允许推进局末剧情；不能复用只在 `Active` 状态接受的普通事件命令，否则会卡死在终局。
- 后端在 `CampaignProgress.Settle`、奖励发放及 `BattleSettlement.Settle` 之前统一检查局末剧情完成门槛；先锁定结果快照，剧情结束后再提交进度、奖励和结算回执。前端只有收到后端“已结算且局末剧情完成”状态才打开窗口，取消已排队的旧弹窗回调，防止闪出提前结算窗口。
- 自然播完和合法跳过都进入同一个完成确认；含选项时跳过仍停在未选择处。最后一个步骤完成后解除结算门槛，奖励／解锁按本局结算回执只提交一次，重复确认、恢复、重看不重复领奖。
- 保存终局快照、选中绑定、场景实例、当前步骤／选项、局末完成状态及结算回执。播放中退出恢复当前剧情；剧情完成但尚未结算时直接续结算；已结算恢复结果窗口，不重播、不重新判定结局、不重复发奖。
- 当前剧情尚未结束时触发终局，先完成其已确定收尾，再播放选中的局末剧情；普通待播事件不插入两者之间。局末明确串联的后继剧情全部完成后才能结算，使用同一终局等待门槛。
- 已绑定局末剧情时默认替代旧通用失败对白，避免重复叙述；需要旧对白可显式排入局末序列。未配置相应剧情的关卡保留原结算体验。已配置却缺失或损坏的剧情需提供重试／恢复及显式跳过出口；有未决游戏选择时不能自动补选或伪造完成。

特殊失败示例：保护目标阵亡 → 裁决失败并锁定 `failure.commander_lost` → 播放人物战败结局 → 完成／合法跳过 → 失败结算窗口。不同胜利示例：满足谈判胜利目标 → 锁定 `victory.negotiated` → 播放谈判结局 → 胜利结算窗口；完全胜利则选择另一绑定。

## 8. 性能与异常策略

按当前剧情预加载开场必需素材，随后预取下一小段；人物常用表情可共用缓存。不能把全部关卡背景和所有人物表情一次性解码。使用有容量上限的已解码图片缓存，结束时释放未引用素材和计时器。

以 1920×1080 RGBA 背景为例，解码后约 7.9 MiB；人物多个全尺寸图层也会累计占用。需在手机实测确定尺寸和缓存预算，压缩后的文件体积不能代替运行内存评估。第一版优先 DOM 图层和 transform／opacity 动画，复用现有前端方式；只有实际性能证据表明必要时再引入额外渲染器。

导入时校验资源存在、路径范围、格式、尺寸／数量上限、角色和部件组合、步骤／选项 ID、分支目标、条件／结果、调用键、文本引用及动画参数，检查所有分支可结束及静态调用循环。错误应指出场景、步骤和资源。运行时缺非必要图片可降级到文字和占位；损坏脚本或全部选项不可用时提供重试、恢复检查点或保存后退回菜单的出口，不能自动代选、伪造完成或留下无法解除的战局锁。Mod 更新后的旧节点无法映射时，保留原存档并提示版本不兼容，不能重做已执行结果。

## 9. 实施阶段与验收

1. 参考图确认：定背景裁切、立绘站位、对话框／姓名栏、工具区、说话亮度和手机布局；用一小段实际图文确认效果。
2. 最小可用播放器：背景、2 至 4 人、姓名正文、剧情内选项与分支、手动／自动、四档倍速、遇选项停下的跳过及触摸处理。先用一个隔离示例检验视觉。
3. 素材接口：角色目录、整图与分层、姿势／表情、动画、资源导入校验；给出最小作者示例和说明。
4. 游戏接入：开场／事件结果／局末三类入口、剧情条件查询、选项复用事件结果、统一等待与排队、结果续接及完成事务、局末路由与结算门槛、分支存读档和旧内容兼容。
5. 双端验收：桌面与手机多比例、Chrome70 兼容路径／实际 Android WebView、连续播放与内存、异常和重启恢复；最终通过后再按用户后续要求打包。

最低验收包括：三人轮流说话且明暗正确；同人换表情／换姿势无错位；移动与跳动可并行；长句完整；自动与倍速可切；连点不串句；后台返回不连跳；缺图可退出；剧情中 AI 不推进；未配置剧情的原关卡正常运行。新增闭环验收：开局只调用一次；事件及旧弹窗结果可调用；剧情选择进攻后走进攻台词并只扣一次费；禁用选项不能提交；自动／跳过停在选择处；剧情选择／完成／结局条件能触发后续事件；重复调用不借用上轮记录；待选／已选／已完成三个阶段存读档均一致；跳过不重复领奖且不漏执行事件尾部结果；串行调用和胜负结算无等待死锁。最终保留最小 Mod 示例源码，完成测试后按仓库规则清理临时产物。

局末专项验收：不同胜利结局分别命中正确场景；特殊失败优先选中对应剧情；同时满足目标只裁决并调用一次；严格先剧情后结算；已结束世界仍能推进／选择剧情；局末选择不能反复触发胜负；跳过遇选择停下且结束后只结算一次；播放中／已播完未结算／已结算三个阶段读档恢复正确；普通事件不抢占结尾；已绑定失败剧情不再重复默认失败对白；未配置剧情时原结算保持。
