# PixiJS替代Canvas 2D建议：项目适用性评估

2026-10-23。用户提供聊天截图，建议“必须接入PixiJS替换Canvas 2D”，理由是“Canvas 2D API太老、性能很低”。本文件将截图作为待评估意见，不作为实施指令。当前仍遵守仅记录报告、暂停实现；没有接入依赖、改代码、运行新实验或构建发布。

最新范围纠正：用户认为并行完成优化后的Canvas和Pixi两套方案再实机选型过于耗费资源，明确要求当前只做纸面评估。已撤销双路线实现/对比选型建议，不将这类实验作为选型前提；未来如获准实施，选定一条路线后做正常正确性及性能验收即可。

## 判断

**GPU批量绘制的方向适合本项目，PixiJS是合适的候选；“因为Canvas 2D老，所以必须换PixiJS才能解决”证据不足。** 应根据本项目实机瓶颈决定渲染后端，不以API年代判断性能。重复计算、增量传输、分块预热、兵牌LOD、动画调度、战略与存档优化仍全部必做，不因更换渲染框架而取消。

Canvas 2D不等于纯CPU软件绘制，浏览器可以对部分绘制与合成使用GPU，实际路径取决于WebView、设备及操作组合。PixiJS采用的GPU渲染后端也不会自动把应用的JS循环、动画树求值、JSON解析或C#逻辑搬到GPU。

已有测量来自[性能审计](PERFORMANCE_AUDIT_20261023.md)，不是PixiJS对照实验。尚未测得迁移后的帧率、耗时或内存，不能承诺固定倍数。

## 针对当前问题能解决多少

### 是否存在“代差”

严格来说，不是同一层级产品之间的新旧代际替代。HTML canvas是绘图承载元素；Canvas 2D是浏览器提供的二维绘制接口；WebGL/WebGPU是另一类GPU接口；PixiJS是组织场景、精灵、图集和批次的渲染库，具体GPU后端依版本及环境而定。Pixi也可以在canvas元素上输出。

但针对本项目的大量动态精灵、粒子、缩放和层级组合，存在实际的架构能力差异：Canvas 2D通常由应用逐条提交绘图命令，图集管理、场景对象、裁剪和复用等主要自行组织；Pixi提供面向这类工作负载的对象/纹理管理与GPU批量绘制机制，更便于将变换、采样、混合和部分效果交给GPU。浏览器也可能批处理或加速Canvas 2D，不能把二者说成“CPU对GPU”。

因此可将迁移理解为从自建Canvas战场绘制层转向专门的GPU二维渲染架构，属于实质性架构升级方向；不能由此推导所有绘制更快或固定倍数的性能提升。静态/少量元素的Canvas场景可能已经很便宜，Pixi的对象遍历、批次拆分和纹理上传也有成本。纸面上可作出倾向性选型，无需先做两套完整实现。

| 已确认的问题 | PixiJS能否直接解决 | 仍需落实的工作 |
| --- | --- | --- |
| 大量兵模、兵牌、头像、特效的位图变换与绘制 | 适配图集、复用对象和纹理后，批量提交可降低部分CPU调用开销 | 裁剪、LOD、层级顺序、纹理预算和动画求值复用 |
| 粒子染色、旋转、透明度和加色 | GPU纹理染色与批量精灵有潜力，部分混合/遮罩需额外处理 | 保持颜色/透明度/混合等价，避免每帧生成染色canvas再上传 |
| 地形大缓存重建尖峰 | 单纯替换最终drawImage不能消除，RenderTexture整体重建也可能卡顿 | 地图分块、按依赖失效、限制更新量、预热与复用 |
| 海岸/国界模板在JS中逐像素生成 | 保留原rasterize时仍然占CPU | 预热模板，或专门改为网格/着色器实现等价插值；收益来自算法迁移而非库名 |
| C#世界验证、候选模拟、深复制与战略搜索 | 不解决 | 已列C#优化全部保留 |
| 每步完整地图JSON的序列化/解析 | 不解决 | 普通/快进增量协议及必要的重同步 |
| 自动存档编码与Flush(true)等待 | 不解决 | 存档管线优化并保留恢复边界 |
| 当前约30Hz动画节流及额外演出等待 | 不自动解决 | 动画调度与时钟设计，确保仅有一个渲染调度源 |

前期桌面样例热缓存约2–3ms，而新区域约147–393ms长帧；两征服快进中完整世界验证调用链约占45%。这些数据不支持“只换Pixi就能治好拖动和52秒过回合”的结论，也不排除手机GPU/提交开销能从迁移中获得明显收益。

## 本项目迁移的适配点和成本

现有`manifest`图集、兵种外观映射、BILE动画解析、镜头坐标和资源管理可复用。C#核心与前端已分离，能够保留规则/存档，替换战场绘制实现；无需为了Pixi将AI改写成JavaScript或重做整个UI。

但这不是替换一个包名：

- `app.js/animation()`使用嵌套图层、变换矩阵、透明度、方向和不同playback_mode。需要把同一时刻的姿态映射到可复用精灵/网格；不能每帧重建整棵显示对象树。
- `battlefield.js`已处理地形前后景、建筑、单位、旗帜和将领头像的遮挡顺序。图集不同、混合模式不同或严格绘制顺序会拆分批次，不能假设所有单位和特效能合成一次GPU绘制。
- `effects.js`含multiply/destination-in染色和lighter加色。Pixi的颜色与混合路径必须与原效果比较，不能把所有组合都当成简单tint替代。
- `map-surface.js`的海岸/边界栅格化是实测热点。若只把其输出canvas变成Pixi纹理，原生成成本仍在；若反复上传大画布，还可能增加CPU→GPU传输。需要专门选择缓存预热或网格/着色器路径。
- 中文、数字、地理标签的字体与密度要求保持；静态文字只在内容/字体/密度变化时更新。允许Canvas生成少量文字纹理并复用，使用Pixi不代表禁止一切Canvas 2D。
- Android宿主最低Android 8，但WebGL/WebGPU能力由具体WebView与GPU环境决定，不能只凭系统版本推断。应按候选Pixi版本核查WebGL要求、纹理尺寸、显存预算及上下文丢失恢复；不能把WebGPU作为所有目标设备的前提。回退优先保留原版本或明确不支持提示，不要求并行开发维护第二套优化渲染器。
- 延续离线运行，库和资源随包提供，不依赖CDN；暂停/恢复、清晰度、坐标点击和Mod额外图集都要覆盖。

## 纸面选型建议

1. 按现有工作负载、图集/BILE资产、Android WebView宿主、长期维护成本评估一条主路线，不开发两套同等优化版本供选型。
2. 若决定对战场渲染层作结构性改造，纸面上倾向采用PixiJS的WebGL路线：它与大量二维精灵/粒子和图集资源相匹配，可减少自行维护GPU批绘基础设施的工作。具体版本及设备能力仍需核查，当前不依赖WebGPU普及。
3. 保留已有动画解析、规则/状态、镜头及DOM界面，把表现接到选定渲染层。避免为了换框架把整个客户端重写；少量静态文字可继续用Canvas生成纹理。
4. 全部既定优化同时保留：分块、预热、LOD、增量传输、C#重算与存档优化不被框架替代。单路线完成后的常规验收检查外观、动作时序、帧时间、内存及完整回合耗时，对照现有基线即可，不要求第二套优化后端。

当前结论：存在面向游戏场景的架构优势，不能简单称为Canvas落后一代；若选择重构战场渲染层，纸面倾向PixiJS/WebGL，但不声称已经获得某个提速倍数，也不认定其是解决C#瓶颈的手段。用户尚未授权实施或最终确定迁移，继续只记录报告。
