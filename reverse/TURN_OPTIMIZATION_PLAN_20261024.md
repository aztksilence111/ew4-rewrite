## 2. 优化后热点与优先顺序

以下时间和分配来自优化后深探针热样本，时间采用独占口径；只用于定位，不作为无探针总耗时占比，也不作为APK实机成绩。

| 热点 | 每轮调用数 | 独占时间约值 | 独占累计分配约值 |
| --- | ---: | ---: | ---: |
| `Movement.DistancesTo`（探针名 `HexMap.DistancesTo`） | 1764 | 870毫秒 | 465 MiB |
| `WorldState.ValidateCore` | 3535 | 799毫秒 | 595 MiB |
| `WorldState.Copy` | 612 | 215毫秒 | 531 MiB |
| `AiTacticalRules.Validate` | 90437 | 140毫秒 | 186 MiB |
| 强制保存flush | 19 | 1293毫秒 | 很小 |

推荐顺序：测量与边界测试补齐 → P1-B距离搜索 → 战术规则冻结与校验复用 → 按来源证据选择A3候选增量校验。各批独立对照，不将全部变更一次合入后才测量。深复制、保存和AOT分别建立后续实验。

### 2.1 P1-B：距离搜索容器与临时分配

主要位置：`rewrite/Ew4.Core/HexMap.cs`、`rewrite/Ew4.Core/WorldAiStrategy.cs`。

1. 诊断记录搜索访问格数、队列入队/出队、过期条目、距离场缓存命中和淘汰，先确认重复工作的来源。
2. 对距离数组、访问代次或临时缓冲区复用做独立实验，减少每次搜索创建字典和树节点的成本。
3. 比较堆队列与现有`SortedSet`，明确保留“成本、格号”的排序、邻接遍历顺序、等成本更新规则和过期条目处理。不能依赖普通优先队列对同优先级元素的未定义顺序。
4. 区分临时工作区与返回结果的所有权。被缓存或仍被调用方使用的距离场不能指向下一次搜索会覆盖或已归还池的缓冲区；嵌套调用也不得共享正在使用的工作区。
5. 当前距离场缓存达到8项后全部清空。先根据命中与复用距离决定是否改为有界淘汰，不直接扩大为跨世界、跨回合缓存。
6. 只有状态及全部通行条件相同才能复用距离场；地形、占位、运输、海岸方向、河流、移动预算、规则和敌我关系均属于需核对的条件。

验收：可达集、距离成本、选择路径、候选顺序、评分、RNG抽样次数与最终状态一致。覆盖同成本路径、边界地图、运输、单向海岸、河流、占位和外交变化。搜索段时间与分配各下降30%可作为工程目标，不是收益承诺；总耗时必须另行测量。

### 2.2 静态战术规则冻结与校验复用

主要位置：`rewrite/Ew4.Core/AiTactics.cs`及规则加载/复制边界。

- 优先处理仍约9万次调用的`AiTacticalRules.Validate`，冻结其字典、修正规则列表及修正规则内嵌套集合。
- 验证成功后只为引擎持有的确切冻结对象复用证明；外部可变对象、record克隆、反序列化结果和新Mod定义不能继承证明。
- 公共可变输入继续原校验。不得仅凭ID、revision或`IReadOnlyList`接口认定不可变。
- 加入原数组/字典修改、非法克隆、Mod重载和旧快照隔离用例，独立测量本批收益。

### 2.3 A3：先拆来源，再缩小候选校验范围

主要位置：`PlanningScope.cs`、`WorldState.cs`、`WorldActions.ProjectMove/MoveCore`和`WorldAi.TacticalMoveCandidates`。

先在隔离诊断中按规划基态、候选模拟、真实执行、提交、保存分组，记录完整校验、证明命中、回退原因及实际格/单位访问量。计数应在真正执行检查的位置，不通过改名或搬移循环制造下降。

当前3535次完整校验涉及2659个不同世界对象。同一对象的重复检查只有876次，即便全部可以省去，仍高于原4251次减半所需的2125次。因此单纯按相同对象身份去重不足以完成原目标；同时不能把876次都假定为可安全删除。

首批仅支持能证明完整变更范围的内置移动候选。变更集必须来自受控写入路径，覆盖路径、移动力、单位、占格容量、领土和关联约束。移动还可能引发投降、事件、外交或胜负变化，不能只检查起终点，也不能为生成变更集再全图比较。

未知变化、脚本、未覆盖的事件/结算影响一律回退完整路径；候选评分前完成必要检查，真实选中动作提交后继续完整校验。开发验证对同一候选进行完整/增量双跑，比较有效性结论，非法公共输入保留错误码与拒绝行为。双跑不进入正式计时。

原“完整校验减少50%”目标仍以4251次为分母；若下一批改用3535次基线，须明确说明，不能混用分母。不能以达标为由放宽检查。

### 2.4 后续独立工作

- 世界结构共享：当前复制仍约531 MiB/轮。需单独证明旧快照、撤回、读档和脚本隔离，首批A3不同时重写动态世界结构。
- 保存：先检查编码和缓冲区重复分配，再评估持久日志或检查点设计；保留每势力/事件的持久性语义、原子替换与强制flush。增加崩溃、写入失败和恢复测试。
- AOT：同源码仅变更编译配置，核验实际产物，再对照手机启动、首轮、热运行、包体、内存与兼容性。无实机收益证据不采用。

## 3. 桌面筛选与APK验收必须分开

验收链：桌面正确性与性能筛选 → 构建并核验APK → 同机整轮对照。

桌面重复测试用于定位计算、分配和回归，不能证明WebView交互、Android运行时、手机存储或设备温控下的实际收益。APK哈希和包内程序集核对证明测试包身份，不证明运行更快。

### 3.1 桌面自动化测量

- 每次从相同固定档、相同双RNG起点运行；不能用连续推进的不同回合作重复样本。
- 保持Release、快进batch、delta=1、trace=0和既有软预算/保存边界。正确性trace和深探针另跑。
- 两图都测性能。每版建议至少5–10次热样本，前后版本交替分组串行运行；首轮单列，热样本报告中位数、范围、分配、GC、请求数和最大请求时间。
- 分别记录进程启动、场景加载和首次计时的边界；不能把已加载内容后的首次过回合叫作冷启动。
- 当前旧基线只有两个热样本，新一轮应对前后版本按相同新协议重测，避免直接把旧均值与新中位数作正式比较。

### 3.2 APK同机整轮对照

主指标：点击结束回合到最终状态已呈现且玩家重新可操作的总时间。继续使用用户现有默认省略动画快进方式，征服1法国固定开局作为主要场景，征服4作为补充。

| 样本类型 | 操作方式 | 计时边界 |
| --- | --- | --- |
| 进程重启后的首轮 | 结束应用进程，启动APK，载入固定档，再过回合 | 点击结束到重新可操作；启动/加载另列 |
| 热样本 | 保持进程存活，每次重新载入同一回合起点，再过回合 | 同上，不包含重新加载耗时 |

- 同一手机分别运行优化前、后APK；每版先收集3–5次热样本，首轮另列。有条件时增加重复，少量样本不报告稳定p95。
- 前后版本交替分组，记录设备型号、系统、充电状态、温度/发热情况及后台负载，避免温控和测试顺序成为主要差异。
- 两版使用相同档案、设置、规则及资源；固定初始RNG。保留用户原档，测试使用隔离档案或明确的测试槽位，不用推进真实存档来重置实验。
- 更新安装后的首次启动若含迁移/缓存建立，单独记录，不混入热样本。不同版本的存档兼容需先确认，不能以卸载清数据作为默认切换方式。
- 继续允许录屏计时，不要求连接电脑、ADB或先提供分段遥测。手机分段诊断是可选项，不阻塞后端优化。
- 没有实机结果时，结论只能为“桌面收益已验证，APK收益待测”。原手机整轮下降30%的阶段目标必须由同机对照验证，不能套用桌面百分比。

### 3.3 可选测试包轻量计时

如后续决定实现自动计时，可在测试包内记录：

1. 前端点击结束回合的单调时钟时间。
2. 所有AI请求、后端计算和保存完成，以及最终状态应用的时刻。
3. 输入恢复且最终状态对应绘制帧完成回调的时刻；该时刻与起点必须处于同一时钟域。
4. 测试结束后显示或导出总耗时、场景、步数、停止原因、版本标识及可核对的最终状态/RNG摘要。

后端分段使用后端自身单调时钟，不能直接与JS绝对时间戳相减。摘要计算、导出和界面展示安排在主计时之后；保证输入恢复标记不早于最终状态应用。

绘制帧回调不能严格证明像素已经显示到物理屏幕，可用录屏抽查与体感边界是否一致。前后APK采用相同轻量计时逻辑；详细方法探针放在独立诊断构建，不能混入正式性能成绩。自动计时是待实施方案，当前APK不宣称已具备。

## 4. 输入指纹与证据留存

测量前建立清单，测量后复核；清单和结果保存在各批独立证据目录。相比当前运行源码清单，补充以下输入：

| 类别 | 内容 |
| --- | --- |
| 源码与驱动 | 运行源码、项目文件、测试驱动、注入器及汇总脚本的SHA-256 |
| 内容 | 本次读取的地图、规则表、资源配置和初始测试档SHA-256 |
| 构建 | SDK/运行时版本、依赖锁定信息、构建命令及属性、目标架构、AOT/裁剪配置 |
| 产物 | APK大小与SHA-256、包内资源/程序集核对结果、版本和签名标识 |
| 运行 | 平台、设备/系统、测试设置、初始双RNG、样本顺序、模式及停止条件 |

比较前后完整文件集合及内容，新增/删除也算变化，不能只核对旧清单中仍存在的文件。记录预期变更清单，出现未解释漂移则该轮结果不能用于归因。资源应冻结或验证测量前后未变；日常复核优先用已有哈希与缓存，不反复扫描无关大文件。

这些证据用于确定比较对象和排除混杂变量，不替代实机计时。各批保留原始样本，不只保存均值和成功布尔值；保存必要测试输出、构建日志及运行命令，便于区分实际重跑与记录核对。

## 5. 作用域嵌套与回调失效测试

当前`PlanningScope.Dispose`恢复外层作用域。此前检查没有证明当前内置调用路径能触发“可信外层→禁用内层修改基态→返回外层”的问题，因此以下是扩大复用范围前的边界验证，不是已确认的现有故障。

| 用例 | 设置 | 预期 |
| --- | --- | --- |
| 禁用向下传播 | 可信外层进入禁用内层，内层再创建通常可启用的子作用域 | 整个禁用调用树不能命中动态证明 |
| 异常退出 | 内层抛异常，经正常清理退出 | 作用域嵌套恢复正确，后续独立调用无缓存泄漏 |
| 回调修改基态 | 外层验证可变世界，禁用内层修改其共享数组后退出，再在外层验证 | 必须检出非法状态，不能复活旧证明 |
| 修改后抛异常 | 内层修改基态后抛异常，外层捕获并继续 | 失效行为仍然有效，不因异常绕过清理 |
| 克隆与字段包装 | 普通with克隆、非法字段克隆、内部仅AiRandomState包装分别校验 | 只有已证明不改变合法性约束的内部包装允许继承证明 |
| 调用结束与后续调用 | 首次调用后修改原集合，再次从公开入口调用 | 必须重新校验 |

测试优先通过真实内置/脚本调用构造，必要时使用仅测试可见的内部入口，不为生产公开API增加`trusted`或`skipValidation`开关。

如果后续允许禁用内层修改外层已验证的对象，仅恢复外层证明表不够：应清除可能失效的外层动态证明，或以共享失效代次让旧证明不能再命中；异常退出也必须覆盖。若选择禁止此类嵌套，则需在入口明确保证，并以测试验证该约束。任意脚本回调前的动态证明不能未经重新确认就跨回调继续使用。

## 6. 每批交付与停止条件

每批交付包含：具体改动、输入/产物指纹、独立正确性结果、未注入桌面样本、诊断工作量、已完成或待完成的APK实机结果，以及仍未验证的边界。

正确性门槛保持两图逐步世界/事件、候选选择、双RNG、步数和停止边界等价；保留Mod、脚本、运输/海战、将领、暂停恢复、事件选择、撤回和保存持久性相关验证。发现顺序、状态、快照隔离或恢复能力变化，应先定位并回退有问题的实验，不用性能收益抵消正确性问题。

本规划不要求为了达标删除候选、减弱AI、改变批处理软预算、取消保存或flush，也不建议再次更换渲染框架。桌面通过但手机未测时允许保留阶段成果，明确标记待验，不能宣布APK目标完成。
